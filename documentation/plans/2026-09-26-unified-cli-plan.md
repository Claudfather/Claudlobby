# Unified Claudlobby CLI

## Summary

**Inferred — finalized design:** build one public `claudlobby` CLI covering all supported system operations. Every bot receives the executable and a concise operating skill by default. Each operation has one implementation and policy owner; its CLI, hooks, scheduled jobs, and integrations use that owner. Existing shell and stdlib algorithms may remain private implementation details. Delete replaced public scripts and migrate their callers together; ship no shims, aliases for retired script APIs, or legacy execution branches. This adopts the operator's decisions after the [#1747](https://github.com/Claudfather/Claudlobby/issues/1747) review.

**Inferred — finalized work model:** a task belongs to a fleet. That fleet has exactly one manager, who owns intake, assignment routing, and follow-up implicitly. A worker assignment is optional at admission and distinct from delivery. The operator clarified on 2026-09-27: tasks remain fleet-owned and an assigned bot can acknowledge. Record that bot's acknowledgement against its specific assignment; it does not transfer task ownership, complete the task or acknowledge unrelated fleet items. Filer, assigner and acknowledging bot remain provenance; none becomes an extra accountability field. This is the operator's fleet-first amendment to [#1739](https://github.com/Claudfather/Claudlobby/issues/1739).

**Status:** design baseline finalized; external team review, implementation and runtime acceptance remain outstanding. The initial stress test and one nine-lens Sol Ironclad pass are complete. On 2026-09-27 the operator explicitly requested one additional, bounded filesystem/architecture coverage pass; its corrections are incorporated below. The operator subsequently approved renovating the existing CLI, first-class messaging/orientation, and aligned domain vocabulary. This revision folds those decisions into one target contract and explicitly inventories migrations. P0/P1 may begin independently once authorized. O1 is resolved below: ordinary communication continues during recording outages with a fleet alert; task mutations still require committed recording. Merge readiness still requires successful checks and the expected additional team reviews covering the amended revision. Further review concerns concrete contradictions or failed acceptance checks, not another broad planning cycle.

### Operator decision O1 — communication continues during recording outages

**Operator decision, 2026-09-28 (UTC); I contract:** ordinary messages and reports without a task should still go through, and a fleet alert should say recording is down. This selects send-with-explicit-degradation over the earlier record-before-every-send recommendation. Task admission/assignment/transitions and linked reports still require committed facts; failed task operations never silently become unlinked messages/reports. Existing dispatch/report doors already separate send availability from recording. [dispatch-task.sh:783][rv-send] [report-back.sh:429][rv-report-send] [Ravi follow-up][ravi-followup]

**Tradeoff:** communication can help recover the recorder, but an unrecorded send has weaker audit/retry evidence. Keep identity, permissions, recipient resolution and transport safety checks. Record first when possible; after a bounded recording failure, ordinary communication may send with explicit recording/delivery outcomes and no automatic retry. Use the existing notification/transport owner for a bounded, debounced fleet alert whose delivery does not require plane recording. The detailed contract below owns this case; no parallel messaging implementation, generic offline queue or new alert service. No implementation is authorized by this document.

## Architecture

### Canonical vocabulary and ownership

**I — accepted direction, 2026-09-27:** design the target interface around the domain. Existing commands are a capability inventory, not a requirement to preserve names, output formats or implementations. No aliases for replaced public commands. Reuse correct algorithms and safeguards, then migrate their callers as one bundle.

| Public noun / Python domain model | Meaning and operation owner | Storage boundary (R/I) |
|---|---|---|
| `task` / `Task` | Fleet-owned work. Task operations own admission, routing and terminal task state. | Existing `work_items`, `work_item_id` and `wi_` identities; mapping to public `task_id` is explicit. |
| `assignment` / `Assignment` | One bot's assignment to that task. The SAME task operation owner validates acceptance, progress and completion under the task lock. | Existing `assignments`/task events; no per-assignment manager or ownership transfer. |
| `message` / `Message` | Communication with delivery attempts and optional task/assignment/reply links. Messaging owner handles all sends and receipts. | Existing `communications`, `msg_id`, reply links and transmission events; public key `message_id`. |
| `request` / `RequestReceipt` | One retryable command invocation and its known effects, keyed by request UUID. | Versioned durable operational receipt; never another task ledger. |
| `fleet`, `bot`, `project`, `host` | Domain identities; config and observed state use distinct models such as `FleetConfig`/`FleetStatus`. | Existing manifests, registry and observed facts remain authoritative for their respective fields. |

**R:** the plane already separates these constructs and requires a fleet on new task/assignment/message envelopes, although its historical SQL columns can be NULL. [contracts.py:168][d-required] [kernel.sql:88][d-tables] **I:** one storage codec at the existing emit/read boundary maps canonical names to the plane protocol; do not duplicate business models or retain old public command aliases. Preserve all historical IDs, hashes and provenance. Physical table/prefix renames buy no user behavior and are not required for naming alignment. CLI flags classify as object selectors, operation inputs, context (`--fleet`, `--request-id`) or presentation (`--json`); not every flag is an entity property. No class per verb, generic CRUD framework or automatic exposure of model internals.

**I — acknowledgement semantics:** `assignment accept` is the assigned bot's acknowledgement that it takes this assignment; it emits existing `accepted`, names the current assignment and actor, and never transfers fleet ownership. A transport receipt only proves delivery. Report acknowledgement is a separate, explicitly selected reader's seen-position; it neither accepts nor completes a task. `fleet inbox` is a projection of fleet work plus that viewer's unseen reports/alerts, not a new queue or a claim that one reader cleared the whole fleet. This keeps the operator's task-ownership ruling distinct from report reading; preserve current per-viewer report cursors. [Operator clarification; contracts.py:93][d-events] [brief.py:318][d-ack]

**I, based on E1–E16 and F1–F5:** the CLI is the public interface, not a requirement to execute every hook inside Python's full application process.

Use existing `commands/`, domain modules, and `plane/`. Add `claudlobby/operations/tasks.py` for orchestration and a small `claudlobby/context.py` for resolved installation/fleet/bot context. Put private native resources under `claudlobby/_native/`; generated hooks/units use their release-bound absolute paths. Register new packages/resources in `pyproject.toml`. Do not build a generic operation framework, second supervisor, or daemon RPC system. The CLI can delegate to a private native implementation that remains the sole owner. [E6, E10, E16]

**Context ownership:** `Paths` plus the new context object owns install/data root and fleet/bot identity for Python. Pass resolved identity to private adapters. For shell assignment semantics, retain `env_tier_rows` and sourcing as one private shell implementation initially; Python queries it, as today. YAML parsing belongs to the Python config loader; generate the minimal resolved roster/context native watchdogs need, rather than retaining a competing shell YAML parser. Invalid/missing context refuses actions that could otherwise broaden scope. Preserve explicit empty environment assignments. [E2, E13; #1608, #1626]

**Availability and permissions:** compose the CLI path and operating skill for every bot without individual tool equip/symlink lists. Translate existing grants to exact new verbs/scope; do not add blanket `Bash(claudlobby:*)` grants. Default identity comes from generated context; explicit cross-fleet targets must be validated against existing policy. Actor/filer fields are provenance claims under same-user trust, not authenticated identities. Host activation, destructive actions and source updates retain their existing operator gates. Preserve opt-in shared-config isolation: its code-Edit deny and freshbox drift checks must follow the release store, not obsolete data-root code paths (#1665/#1918). [E12, F4]

**Coaching source:** CLI argument definitions and structured output own the machine contract. One fleet-operations skill teaches discovery, read → act → verify, retry IDs, and failure handling. Composed `CLAUDE.md`/`AGENTS.md` contains a short pointer and invariant, not another command catalogue. Default managers consume fleet intake during check-in; workers report using the assignment ID in the delivered envelope. Keep engineering workflow behavior outside this fleet-operations skill. [E15; #1747]

### Agent skill and permission delivery contract

**I — concrete implementation of the default skill requirement:** ship `library/skills/fleet-ops/SKILL.md`, invoked as `/fleet-ops` where slash skills are supported. Its description triggers for checking fleet/task state, admitting/routing work, reporting progress/results, and permitted bot operations. Include it in every bot's effective skill set automatically, with a short composed instruction to consult it for fleet operations. No per-bot equipment list, manual script symlinks, or separate installation step. Package skill, CLI and generated grants in the same release. [F1–F2; E12, E15]

The skill is an operating guide, not a second executor. It teaches: identify current bot/fleet from generated context; discover verbs through `--help`; read state with `--json`; select the right operation; save/reuse request IDs; verify recording and delivery separately; treat `recording_degraded` as a possible completed send, inspect the returned transport/alert outcome and never auto-retry it; and stop on permission, scope or release errors instead of improvising SQL, raw events, shell helpers or tmux sends. Keep a few complete examples for worker reporting, manager intake → assignment → delivery, and diagnosis; reference command help for detailed flags. Existing check-in/status/restart skills call the same CLI and reference this guide rather than copy its contracts. [I; E3, E8–E9, E15; #1747]

**R:** skill invocation and the tools used inside a skill are separate permission layers: [composer.py:2353][skill-invoke] derives `Skill(...)` grants; [composer.py:2368][skill-tools] resolves `tool_grants`; [composer.py:2623][skill-compose] composes both from the effective skill set. **I:** extend those owners rather than inventing another permission installer. The universal skill carries common invocation/read grants; the composer supplies operation grants appropriate to the bot's existing fleet policy and manager role. Do not put manager/host privileges in universally inherited skill frontmatter.

| Recipient | Generated permission intent (I; E12, F3–F4) |
|---|---|
| Every bot | Invoke the skill, CLI help and relevant reads; admit work into its own fleet; report against its own assignments or explicitly submit an unlinked report to its manager, as permitted by fleet policy. |
| Fleet's manager | Additionally route, deliver, reassign and follow up on its fleet's work; receive only the lifecycle/notification rights its policy allows. |
| Operator / explicitly privileged bot | Host activation, source updates, destructive teardown and cross-fleet operations remain explicitly granted or approved. Universal CLI availability adds none of these automatically; explicitly scoped coordinator admission into a destination fleet preserves its existing cross-fleet responsibility without bypassing that fleet manager. |

Use one canonical command spelling in agent examples and generated rules—for example `claudlobby --json task show TASK_ID` with generated context supplying scope. Exact rule syntax must match the actual runtime and argument ordering; a grant for skill invocation alone or a pattern that misses `--json` is not sufficient. Preserve operator denies and existing approval behavior. These are unattended-tool permissions under the agreed same-user trust model, not per-bot authentication or an isolation boundary. [I; E12, F4; skill permission owners above]

### Data model and invariants

1. Add required `fleet.manager: <local bot-id>` to `FleetConfig`, validator, seeds and shipped examples. Exactly one existing bot is the fleet manager. Team groupings may reference that same manager; they cannot introduce a competing fleet manager. Cross-fleet `manages` edges describe reporting relationships, not additional fleet managers. Existing estates explicitly edit ambiguous manifests before cutover; do not silently guess a manager. Update manager-derived defaults, registry keyframes and org chart together. [E4]
2. Task = fleet + stable public `task_id` (stored as `work_item_id`) + title/body/project/workstream + `created_by`. Assignment = stable `assignment_id` + work-item link + worker + `assigned_by` + optional deadline. Do not add `manager`, `accountable_to`, or `owner_bot` to each work item. Resolve current accountability through its fleet; a manager change takes responsibility for all open fleet work without rewriting historical provenance. Validate worker membership and matching fleet IDs. [E3–E5]
3. Admission writes a work item and no assignment by default. One work item has at most one current assignment; concurrent routing must serialize on the work item and refuse a second active assignment. Parallel work is separate work items under a workstream. Assignment creates no tmux message; delivery is another action. [E3; #1739, #1747]
4. Work view states: `queued`, `assigned`, `active`, `blocked`, `completed`, `failed`, `cancelled`. An unassigned work item is `queued`. Accepted/progressed assignment is `active`; waiting is `blocked`; completion/failure closes work. A returned, rejected, expired or withdrawn assignment releases still-open work to `queued`. Reassignment terminates the old assignment and creates its successor in one batch. Work-level withdrawal emits `cancelled` without an assignment ID and closes any active assignment in that batch. Worker inability should use `return`; `fail` declares the work itself failed. Terminal work is not silently reopened. [E3; existing task-event vocabulary at contracts.py:78]
5. Read history by first-class work/assignment IDs, including rows whose legacy display task ID is null. `task list` includes unassigned intake. Update the plane UI, brief, overdue calculation, check-in and recheck to share this reducer; remove source-prefix and assigner-as-manager assumptions. Older terminal history remains closed; the cutover report explicitly resolves any ambiguous historical returned/idless rows before routing resumes. Do not create fake assignments to managers to make the old board show intake. [E5, E9]
6. Reuse existing task/assignment/event storage where it represents the target semantics; the migration ledger below decides SQL changes explicitly. All typed task mutations use one per-task interprocess lock through read/validation/committed batch; assignment actions resolve their parent task before acquiring it, then re-read and validate. Task operations alone own this invariant. Per-request locking prevents duplicate admissions, which do not yet have a task lock. Existing `emit_batch` remains the transactional ingest owner. Raw diagnostic writes are outside the supported task API. [E3, E6; ingest.py:463][d-ingest]
7. New Task operations stamp `emitter=claudlobby.tasks.v1`; reducers retain historical event semantics for older producers and apply the declared new transitions to these facts. No rows are hidden by source prefix. In particular, old returned/expired/superseded terminal history must not spontaneously re-enter intake when the new model returns an assignment to queued work. The A0 cutover report establishes each open task's current assignment and flags ambiguity; no “latest row wins” guess. [E5, E9; migration ledger below]
8. New assignments validate that task, worker, project and workstream belong to the resolved fleet; a bot's assignment acknowledgement uses its current assignment ID and context actor. `--by` is provenance, never an authority override. An unassigned task cannot be accepted, and an old assignee cannot acknowledge the replacement assignment. Refuse mismatches before recording. Project completion policy remains declared data; expose it without claiming the CLI ran the workflow or automatically certifying supplied evidence. [Operator ruling; E3; config.py:256][d-project]
