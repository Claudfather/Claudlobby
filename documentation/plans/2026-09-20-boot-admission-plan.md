# Boot admission and supervision consolidation — plan

## Summary

PR A **has landed** (#1684, `3f26afe`): the one truth (`BootPolicy` into `bot.conf`), the renderer boundary (`SupervisionSpec` and its round-trip test), the supervisor adapter with its ratchet, and the three amplifier fixes (`MCP_TIMEOUT`, a wall-clock readiness ceiling that names why, plugin updates once per boot). PR B moves the boot path onto it: the priority admission gate **replacing the #304 boot lock in place** inside `start-bot.sh`, the platform-neutral boot-progress marker wired into every consumer of `service_is_starting`, and two reboots — one on PR A alone as the control, one on A+B. PR C carries what ironclad cycle 1 showed was neither provable nor deployable inside PR B: the adapter migration of the five boot-path scripts (if F12 lands that way) and the systemd stagger retirement with everything that reads the rung (F11). Mission line: "long-running is the precondition for the rest" — a fleet that cannot survive a host reboot without a storm cannot hold a goal.

## Architecture

Three layers, one owner each, one test at each boundary (spec §5): the core process (`start-bot.sh`, `keepalive.sh`, the lib doors; policy from `bot.conf`, state from markers), the adapter (`lib/supervisor.sh`, five verbs, two spellings), the renderer (`SupervisionSpec`, two writers, idioms only). The gate is the single bring-up mechanism on a host; the marker is the single boot-progress signal; the ratchet keeps every future supervisor call inside the adapter.

**One correction cycle 1 forced into this picture.** "The gate is the single bring-up mechanism" was written as if the host had none. It has one: `lib/start-bot.sh`'s #304 boot-mass mitigation (`:14-47`), a platform-neutral `mkdir` lock that runs on launchd today and appears in **zero** lines of the original spec, epic and per-PR plans. The gate is therefore an *extension of an existing mechanism*, not a new one, and PR B deletes the lock in the commit that lands the gate (F9). Until F11's PR C lands, a systemd host also still carries the composed `ExecStartPre` ladder — so "no per-supervisor expression of that policy anywhere" (Goal 2) is **partially delivered** by PR B on the deployed host and fully delivered only after PR C. Stated rather than claimed.

## Decision Forks

Design forks are locked in the spec (§11). These are implementation forks. **F1–F8 are locked and cycle 1 re-opened none of them**; three carry amended rationale under the same lock, marked *(rationale amended 2026-09-21)*. F9–F17 are new, from cycle 1.

- **F1 — Adapter placement.** Context: the ratchet needs a greppable boundary. Options: (a) a new `lib/supervisor.sh` sourced by `lib-common.sh` at source time; (b) a delimited section inside `lib-common.sh`. Lean: (a) — a file is a boundary a test can name; a section is a convention. Ratifier: operator. Status: locked (a), 2026-09-20, ratified with the spec's adapter section.

- **F2 — Gate state location.** Context: the gate's queue and slots are shared state that several unrelated launchers negotiate over, so the directory decides the bound's scope. Options: (a) `$CLAUDLOBBY_ROOT/state/boot/`; (b) `$TMUX_TMPDIR`; (c) a per-user dir. Lean: (a). Ratifier: operator (2026-09-20, with the design walk). Status: locked (a) — the only host-wide directory the runtime already owns, and the directory PR A already writes into.
  - *(rationale amended 2026-09-21)* The original rationale read "host-wide because the root is host-wide". **That is refuted**: `CLAUDLOBBY_ROOT` is per-**install**, exported from each bot's own `bot.conf` (`claudlobby/composer.py:882`) and sourced at `lib/start-bot.sh:12`, and a host routinely carries more than one root (a live install, a maintainer checkout, and the exported trees `validate-bot-change.sh` / `coldstart-harness.sh` create). The **correct bound is per install root**: bring-ups from a second root are invisible to the gate, and "a hand run is covered" holds only when the hand run uses the same root. The choice stands — it is still the widest scope the runtime owns without inventing a host registry — but the claim does not, and the plan and spec now state the bound instead of the claim. The residual (each waiter reading the slot count from its own `bot.conf`, so the effective cap is the largest opinion present during a rolling generate) is **F14**, not a re-opening of F2.

- **F3 — Readiness ceiling coupled to the MCP timeout.** Context: a poller that comes up at 150 s under a 180 s MCP timeout would be logged `TIMEOUT` by a 90 s ceiling and alerted on. Options: (a) derive `ready_timeout_s = max(90, mcp_timeout_ms // 1000 + 20)` inside `BootPolicy`; (b) two independent numbers. Lean: (a) — one truth, no way to set them inconsistently. Ratifier: operator (2026-09-20, with the design walk). Status: locked (a).

- **F4 — Precedence between the composed value and an env override.** Context: `start-bot.sh` reads `${RC_READY_TIMEOUT_S:-90}` and `bot.conf` is sourced under `set -a` inside it. Options: (a) the composed `bot.conf` value wins; the env var stays as a fallback when the key is absent (old `bot.conf`); (b) env wins. Lean: (a) — the truth is the composed file; an operator changes `system.yaml` and regenerates. Ratifier: operator (2026-09-20, with the design walk). Status: locked (a).

- **F5 — Ratchet allowlist granularity.** Context: the ratchet has to fence new direct supervisor calls without churning on every unrelated edit to a listed file. Options: (a) `(script, count)` pairs; (b) per-line anchors. Lean: (a) — shrinks freely, no churn on unrelated edits. Ratifier: operator (2026-09-20, with the design walk). Status: locked (a).
  - *Note (2026-09-21, not a re-opening):* `CALL_PATTERN` counts **prose** as well as calls, by design and by its own docstring. Measured post-migration floors are keepalive 3, spin-up 0, spin-down 1, install-bot 1, install-bot-systemd 1 — so only one file can ever leave the allowlist, and `test_allowlist_has_no_zero_count_entries` is consistent with that. The counts are not targets; rewording a comment to reach one is forbidden in PR B's "What NOT To Do".

- **F6 — Round-trip parser for the systemd unit.** Context: the equivalence test has to read back a unit that legitimately repeats a key (`Environment=` appears twice), which the obvious stdlib parser rejects. Options: (a) a small line parser tolerant of repeated keys, sections by `[Name]`; (b) `configparser`. Lean: (a). Ratifier: operator (2026-09-20, with the design walk). Status: locked (a).

- **F7 — Harness scenario vs a rehearsal script for the gate.** Context: the gate needs a runtime proof, and the estate has two shapes for one — a block inside the standing harness every `lib/` change already pays for, or a `rehearse-*` sibling run on demand. Options: (a) a new check block in `lib/validate-bot-change.sh`; (b) a `rehearse-boot-admission.sh` sibling. Lean: (a) — the harness is the runtime gate every `lib/` change already pays for. Ratifier: operator (2026-09-20, with the design walk). Status: locked (a).
  - *(rationale amended 2026-09-21)* The choice stands; the rationale as written buys a test that **passes on a gate that does nothing**. The harness's throwaway bots have no channel (`BOT_SERVICE=""`, no token, `lib/validate-bot-change.sh:1399-1408`), so `bridge_state` answers `no_handle` and `wait_bridge_ready_state` returns on its **first** poll — the first bot's hold is sub-second and "both granted immediately" is indistinguishable from an inert gate. PR B Task 2 Step 6 therefore requires a *controlled* hold (a stubbed `bridge_state`), a **positive control** (the same scenario at 2 slots must show both granted at once), ordering asserted from the **grant log lines** rather than a sampled file, a pinned shared `CLAUDLOBBY_ROOT`, and an explicit stub list **and cannot-prove list** in the plan — the gate rations MCP startup, and the stub spawns no MCP servers, so the one contended resource is absent from the test by construction.

- **F8 — `service_is_starting` signature.** Context: it takes a service name and returns 1 off Linux; the marker lives under the bot dir. Options: (a) `service_is_starting <service> [bot_dir]`, marker rung first when a bot dir is given; (b) a separate `bot_is_booting <bot_dir>` and keepalive calls both. Lean: (a) — one question, one door; keepalive already calls it with `BOT_DIR` in scope. Ratifier: operator (2026-09-20, with the design walk). Status: locked (a).
  - *(rollout amended 2026-09-21)* The signature is untouched; the **rollout of it was one of four**. The door has four production call sites — `lib/keepalive.sh:324`, `lib/fleet-pulse.sh:307`, `lib/fleet-pulse.sh:824`, `lib/validate-bot-change.sh:2469` — and the previous PR B draft wired one. Because the second argument is optional nothing would have failed loudly; fleet-pulse would simply never gain the marker rung and would page on every queued bot. An optional argument makes an incomplete rollout silent, so PR B carries a **door consumer table** and a test that fails when a new consumer appears. Two further consequences of the same signature: `${1:?}` aborts a non-interactive caller on an empty first argument (nine harness `bot.conf`s and every pre-generate fleet carry `BOT_SERVICE=""`), so it becomes `${1:-}`; and the `[ -n "$BOT_SERVICE" ] &&` short-circuits in front of three of the four call sites must go, or the marker rung is unreachable for exactly the bots that have no service name.

- **F9 — ONE mechanism: does the gate extend the #304 boot lock, or sit beside it?** Context: `lib/start-bot.sh:14-47` is already a host-wide bring-up serializer (`bc0990f`/`efa2092`, #304) — a fleet-wide `mkdir` lock, 8 s hold, 60 s stale force-claim, 120 s wait cap, detached release — platform-neutral, running on launchd today, and named in **zero** lines of the spec, the epic or either per-PR plan. Options: (a) the gate **replaces it in place** — same file, same position, same atomic primitive, deleted in the commit that lands the gate; (b) the gate is added beside it, so a bring-up passes two serializers with different scopes (`$TMPDIR` vs `$CLAUDLOBBY_ROOT/state/boot/`), the outer one not priority-aware and fixing arrival order before the gate ever sorts managers first. Lean: (a). Ratifier: **operator, 2026-09-21** — *"Definitely dont want a second mechanism."* Status: **locked (a)**. Evidence: the ruling above; `lib/start-bot.sh:14-47`; `grep -n 'BOOT_LOCK\|boot lock\|boot-mass'` over the whole source bundle returning zero hits; and the lock's own defects (a forward clock step force-claims a live lock, a backward step makes the age negative and it is never cleared; at 18 bots × 8 s against a 120 s cap the tail of the fleet provably ran unserialized on the incident boot). PR B deletes it, drops `BOOT_LOCK_HOLD_S=0` from the harness's six neutering sites, and pins "no second serialization primitive in `start-bot.sh`" with a grep assertion and a mutant.

- **F10 — Where the gate sits inside `start-bot.sh`.** Context: the previous draft said "after `bot.conf` is sourced and before `tmux new-session`" — a span of ~266 lines whose two ends are materially different systems, and the single line of placement with the largest cost swing in the PR. Options: (a) at the **top**, where the #304 lock is, immediately after `load_bot_conf` (`:12`) — the gate then covers the seeding (`:108`, `:116`) and plugin/marketplace phase (`:225-276`, a `with_timeout 60` per unregistered marketplace) that the stagger was spreading, and a queued restart does **not** kill the live session first (`:135`), so a bot stays inbound-live while it waits; (b) at the **bottom**, just above the session spawn — shorter slot holds, but ~21 launchers then run the filesystem- and network-heavy phase concurrently with nothing bounding it, and a queued restart leaves the bot dark for up to the cap with no recovery path. Lean: (a). Ratifier: **operator, via F9** — the mechanism being extended already sits at (a), and "extend, do not add a second" fixes the position. Status: **locked (a)**. Consequence, stated: the hold spans the whole phase, so the hold ceiling is `ready_timeout_s + 120` rather than `ready_timeout_s`, and the drain arithmetic in PR B's Evidence uses that.

- **F11 — The systemd stagger retirement: PR B or PR C?** Context: retiring `ExecStartPre`, `bot_boot_delay_s`, `_host_boot_rung_bases` and `boot_rung_for` changes the runtime behaviour of exactly one host class — systemd. Options: (a) in PR B, as originally planned; (b) in PR C, after the gate is proven. Lean: (b). Ratifier: **operator, 2026-09-21** — *"deploys only to the primary host, never to the Pi."* Status: **locked (b)**. Evidence: the stagger is composed only into the systemd unit, so under that ruling the change can be neither deployed nor proven inside this program; retiring it would also first-exercise the new mechanism in the same deploy that removes the old one, against this repo's own standing posture; and on a four-core host `derive_slots` yields **1** slot for ~21 bots, so retiring the ladder there is plausibly a regression the bridge-tally proof cannot see (`documentation/runbooks/audit-cold-start-timing.md:45-60` already carries a 36 s fully-parallel baseline the gate would serialize). Four cycle-1 blockers and five risks are consequences of this unit and move with it (PR B `## Deferred`, D2–D5). Reversible in one line if the operator intends the stagger retired inside PR B.

- **F12 — The adapter migration of the five boot-path scripts: PR B or PR C?** Context: 25 call sites across five scripts, plus moving the two installers' bodies into `lib/supervisor.sh`, plus the `ExecStopPost` three-spelling fold, for a ratchet shrink of 109 → 84 (23%) and **zero incident benefit** — verified: `restart_bot_service` (`lib/keepalive.sh:189-211`) already ends every branch in `start-bot.sh` directly or as the supervisor's `ExecStart`, so the gate catches every keepalive bounce with the ladder exactly as it is. Against that: it is the largest source of new file churn in the deploy whose own Context line reads "every bring-up on every host passes the new gate", and cycle 1 found five separate defects in the migration as written (`||` vs rc 2; `spin-up-bot.sh` is a three-way with a migration branch, not an enroll; the log breadcrumb inverted and the streams crossed; a wrapper→verb→wrapper recursion on the enroll path `setup-fleet` runs per bot; the ratchet floors are 3/0/1/1/1, not zeros). Options: (a) keep it in PR B; (b) PR C, behind the proof. Lean: **(b)** — cutting it leaves PR B's stated goal fully intact, which is the test for a cut candidate, and the corrections are already written down so nothing is lost. Ratifier: operator. Status: **open**.

- **F13 — The wait cap: the ratified flat 1200 s, or derived and dispersed?** Context: spec §11.4 ratified `1200` as a flat default on 2026-09-20; cycle 1 showed it is not a safety margin but the design's **throughput ceiling**, and that it was never reconciled with the other two numbers. Measured: drain is `ceil(bots / slots) × hold_ceiling`, so the four-core host (1 slot, ~21 bots) needs **4200 s** at the hold ceiling and still **1218 s** at the optimistic 58 s per-bot figure the spec itself measured; the launchd host at 2 slots needs 1800 s. Worse, every ticket at a cold boot is minted within the same second, so a flat cap expires for **every waiter in the same second** and the escape releases the whole remaining queue at once into a host that is by then provably saturated — the storm it replaces, delayed and concentrated. Options: (a) keep the flat 1200 s; (b) **derive** `admission_wait_max_s = ceil(bots_on_host / slots) × hold_ceiling_s` in `BootPolicy` (the F3 move), refuse at compose time to emit a policy whose drain exceeds its own cap, **and** disperse the escape per ticket (`effective_cap = cap + arrival_rank × (ready_timeout_s / slots)`) so it degrades one bot at a time; (c) keep 1200 s flat but disperse only. Lean: **(b)**. Ratifier: operator — this **changes a ratified default** and needs a new ratification, not an amendment. Status: **open**. PR B implements the dispersion and the derivation behind this fork; if the operator keeps (a), the plan still carries the dispersion and states the tail-bot dark time (19.3–66.7 min at 1 slot) as a disclosed cost.

- **F14 — Where the slot count is derived.** Context: `derive_slots` runs in the composer (`claudlobby/boot.py:72-80`; spec §6.1 "`auto` derives … at compose time") and the value is baked into each `bot.conf` under a **synced fleet overlay**. So a `generate` run on a many-core workstation writes that machine's slot count into the target host's `bot.conf`, and a `generate` on a host that cannot report its CPU count writes 1 for a large host. The single number bounding host-wide boot concurrency is the one value in the policy that is a property of the **runtime** host, and it is currently resolved furthest from it. Separately, each waiter reads the cap from its own `bot.conf`, so during a rolling generate the effective cap is the largest opinion present. Options: (a) keep compose-time derivation; (b) render `BOOT_ADMISSION_SLOTS=auto` verbatim and derive at **acquire** time from the host the gate is actually on, keeping the composer's explicit-override path; (c) keep compose-time but have the gate log loudly when the composed value disagrees with the live CPU count; (d) (b) plus reading the resolved count **once** from `state/boot/`, written by the first waiter, so all waiters on a host agree by construction. Lean: **(b)+(d)** — ratified decision 2 says "slots derived from the host", and acquire-time derivation is literally that. Ratifier: operator (it amends a spec §6.1 behaviour). Status: **open**.

- **F15 — The boot grace becomes composed policy.** Context: `service_is_starting`'s window is `KEEPALIVE_BOOT_GRACE_S` / `_BOOT_GRACE_S_DEFAULT = 300` (`lib/lib-common.sh:4182`, `:4264`) — a boot-policy value `BootPolicy` does not own and an env knob an operator can set, against Goal 1 ("boot policy defined once, composed into `bot.conf` once, and read by the runtime from there only") and against "zero configuration". PR B also **falsifies its stated budget**: the comment at `:4170-4180` says 300 s is ">3x headroom" over a phase "bounded by start-bot.sh's own `RC_READY_TIMEOUT_S`", and PR B moves the host-wide wait *into* that phase. Options: (a) leave it an env knob and let the two numbers drift; (b) derive `boot_grace_s = admission_wait_max_s + ready_timeout_s` in `BootPolicy`, render `BOOT_GRACE_S`, and keep `KEEPALIVE_BOOT_GRACE_S` as the **fallback for an un-regenerated `bot.conf`** — exactly the shape F4 already locks for `RC_READY_TIMEOUT_S`. Lean: (b). Ratifier: **operator, via Goal 1 + F4** — a boot-policy value read from an env knob contradicts a ratified goal, and (b) adds no operator step. Status: **locked (b)**. The #933 manufactured-all-clear bound the 300 s existed for is **kept, not widened**: it moves from mtime to **liveness** — the marker names its launcher's pid, and a dead launcher stops suppressing within one poll, which covers the SIGKILL case 300 s of mtime never could. The falsified comment is rewritten in the same commit.

- **F16 — The distributed gate, or a composed per-bot delay?** Context: `claudlobby/supervision.py:172-175` already names a counter-plan — "a BOOT_DELAY env var honored by start-bot.sh itself" — which spec §2 quotes only to note "It was never built." Composing `BOOT_DELAY_S` from the same `BootPolicy` would close the stated divergence, give the launchd host the stagger it has never had, retire `ExecStartPre` and `boot_rung_for`, and introduce **no** shared state, no reaper, no pid liveness, no lock and no clock dependence — on a host whose clock is the known hazard. Options: (a) the admission gate (a bounded-concurrency queue); (b) a composed per-bot delay. Lean: (a). Ratifier: **operator, via F9** — the ruling is that the gate *extends the existing lock*, which is a serializer over the live population, not a per-bot sleep. Status: **locked (a)**, with the counter-plan recorded rather than ignored, and its one sacrifice named plainly: a delay cannot serialize a **keepalive bounce or a mid-phase rolling restart**, which is the case #1573 ask 1 is about and the case a cold-boot ladder never covers. Spec §11.1 rejected "a ladder" because "the ladder's number was wrong by ten times and would be guessed again" — a criticism of the *number*, not of *where the delay lives*, so the counter-plan deserved this paragraph rather than that sentence.

- **F17 — The rollout carrier for a change with no canary window.** Context: `lib/start-bot.sh` is read **on demand, per bring-up**, so the `git pull` — not the manager restart — is the rollout: the first keepalive bounce after the pull runs the new gate on a production bot nobody chose (`documentation/fleet-update-lifecycle.md:346-357`; the same class the package `system.yaml:299-302` ruling covers for this exact file, which is why `inject_stamp` carries `BOOT_CAPTURE_ENABLED`). The previous draft's "pull, generate, one manager restart per fleet" looks like a canary and is not one. Options: (a) name the carrier honestly — Task 5 states that the pull is the rollout, names the pre-pull evidence and names the rollback — and add no flag, because a flag would be the second mechanism the spec forbids; (b) ship behind a per-fleet arming flag defaulting off (throwaway fleet → one production fleet → the rest), the shape `SPINDOWN_RECEIPT_ENABLED` and `BOOT_CAPTURE_ENABLED` already use; (c) both, with the flag framed as a **temporary arming carrier** removed in PR C rather than a policy knob the operator lives with. Lean: **(c)** — an arming carrier is rollout, not configuration, so it does not collide with "zero configuration", and it is the one shape under which a change with no canary window can be canaried at all; but it is a knob, and "no silent switches" means it needs a stated removal step, which PR C owns. Ratifier: operator. Status: **open**. PR B implements (a) unconditionally; (c) adds one gate and one removal row.

## Implementation Plan

### Dependencies

None at epic level. Inter-phase: PR B depends on PR A merged **and deployed**; PR C depends on PR B's reboot proof having been taken.

### Blocks

The ratchet follow-ups (`setup-fleet`, `reconcile-fleet.sh`, the timer installers, the rehearsal scripts) are blocked on the adapter existing, which PR A delivered; they are not blocked on B or C.

### Steps

The epic's steps are its phases. Each expands into the named companion plan; the per-PR `### Steps` are the zero-ambiguity level and are not duplicated here.

- [x] **Phase A — the one truth, the renderer boundary, the adapter and the ratchet, the three amplifier riders.** Merged #1684 (`3f26afe`). Deployed.
- [ ] **Phase B — the gate replaces the boot lock, the marker reaches every consumer, two reboots.** Six tasks (0–5) in the PR B plan, one of them conditional on F12. Gate to C: the reboot proof taken and read against the PR-A-only control.
- [ ] **Phase C — the stagger retired, the rung readers re-based, the adapter migration.** Charter = PR B's `## Deferred` rows D1–D5, each carrying the cycle-1 correction it needs. Not started; written after B's proof, because two of its rows exist only to be decided by that proof.

## Test Plan

Per-phase test plans live in the companion docs and are the authority. At epic altitude, three properties must hold across the phases and none of them belongs to a single PR:

1. **One boot-timing truth.** `tests/test_boot_policy_conformance.py` asserts every policy key appears exactly once in `bot.conf` and in neither rendered unit — extended by PR B with `BOOT_HOLD_CEILING_S` and `BOOT_GRACE_S`, and by PR C with the absence of `ExecStartPre`.
2. **One bring-up mechanism.** PR B's grep assertion that `lib/start-bot.sh` carries no second serialization primitive, plus the "boot lock returns" mutant. PR C extends it to the composed units.
3. **No silent consumer.** `tests/test_door_consumers.py` (PR B) checks in the consumer map for each changed door and fails when an unlisted call site appears; PR C adds `boot_rung_for`'s rows to the same map rather than repeating the exercise.

The standing gates apply to every phase unchanged: the two-leg names-plus-counts run taken **unsandboxed** against the phase's own base, `bash lib/validate-bot-change.sh` run directly after any `lib/` change, committed-code mutants, CI on Linux, and the macOS red baseline compared by name rather than by count.

## Risks

| risk | impact | mitigation |
|---|---|---|
| The gate strands a bring-up (unwritable state dir, a stuck holder, an unresolvable epoch, an empty unit name) | a bot never starts | every failure path proceeds and discloses (`boot_admission_timeout`, `boot_admission_unavailable`); holders are reaped on pid death **and** on a hold ceiling; the cap is per-ticket dispersed (F13) |
| **The gate degrades into a synchronized release** | the storm it replaces, delayed and concentrated | every ticket at a cold boot is minted in the same second, so a flat cap expires them all at once: the cap is derived from drain (F13) and the escape is dispersed by arrival rank; a `waiters = 3 × (cap/hold)` cell asserts releases are spread, not simultaneous |
| Keepalive kickstarts a queued bot on launchd (livelock) | the storm returns in a new shape | the marker rung lands in the same task as the gate, the marker's ONE lifetime runs acquire → **release** (not to grant), and the harness asserts a keepalive tick leaves a queued bot alone |
| **Fleet-pulse pages on every queued bot** | the alert storm the epic exists to close, re-emitted from the door the plan did not touch | `service_is_starting` has four call sites and fleet-pulse owns two of them; PR B carries a door consumer table, passes the bot dir at all four, deletes the three `[ -n "$BOT_SERVICE" ] &&` short-circuits, and adds a fleet-pulse cell asserting the two consumers agree about a queued bot under `_OS=Darwin` |
| **A restart driver hard-stops on a bot that is merely queued** | `rolling_restart_stalled` FLEET ALERT on the very door the estate uses to recover from this outage class (#689/#688), and on the weekly worker restart | the gate's hold ceiling is `ready_timeout_s + 120` — the **same** margin `lib/rolling-restart.sh:86-104` already derives — and serial callers set `BOOT_ADMISSION_CALLER_CAP_S` to their own per-bot slack, so a serial driver (already the bound) never also pays the queue's cap. The mechanism fix, not two widened ceilings |
| **A serial fleet sweep blocks on one queued bot** | one queued bot stalls every other bot's watchdog on a 60 s timer (`lib/keepalive-all.sh:73-97`, `lib/keepalive.sh:209`) — the sweep-abort class | same scoped cap; a harness cell asserts a sweep with one queued bot completes inside a stated bound |
| **`MCP_TIMEOUT=180000` is below the measured amplitude of the failure** (spec §2 measures the contended MCP phase at "over five minutes") | the amplifier fix does not dominate the event it was derived from, so the whole design rests on the gate never letting concurrency reach the contended regime | stated plainly rather than mitigated: **the gate is load-bearing**. `ready_timeout_s` is derived from it (F3) and must stay under `bridge_down_state`'s 300 s `.spawn` grace (`lib/keepalive.sh:230-232`) or the heal path bounces bots that are still legitimately booting. If the reboot shows the gate holding, this row closes; if not, the timeout is raised (its only cost is slower failure on a genuinely broken server) |
| **The slot formula's independent variable is not the measured constraint** | `clamp(cpu_count // 4, 1, 4)` is a guess with a formula around it; the spec's evidence identifies contention but never identifies what is contended | the reboot records per-bot wait and hold as metric samples, so the formula can be replaced by data from the run that was supposed to validate it; F14 moves the derivation to the host it bounds |
| Removing `ExecStartPre` breaks the `Type=simple` + `RemainAfterExit` triple that makes SubState a boot signal on Linux | keepalive's Linux dead-session watchdog goes blind | the triple test stays; only the stagger line goes; the marker is the first rung on both OSes. **Deferred with F11** — the `activating` arm keeps its producer until PR C |
| **The stagger retirement makes boot worse on the four-core host** | ~21 launchers start at t=0 into `seed_workspace_trust`, `seed_all_checkouts` and the plugin block, on a host where `derive_slots` yields 1 slot | F11 defers it; when it lands, the gate must already sit **above** the seeding block (F10 puts it there) so the gate replaces what the stagger was doing, and `lib/bench-cold-start.sh` measures the serialization cost before/after |
| The ratchet allowlist rots or is bypassed by a rename | a new direct call slips in | counts only shrink; the test greps for the binaries, not for wrappers; a rename of the adapter file fails the test by construction. **The floors are 3/0/1/1/1, not zeros** — chasing zeros would delete real operator documentation |
| The self-start instrument loses its rung-based "not yet due" **and its validity claim** | a measurement page read mid-incident reports a catastrophe that has not happened, or credits every unrecorded wake as good news (#1203) | deferred with F11 (D4), with the replacement bound written down: `VALID_AT` re-derived from the admission window, the three-state answer kept (never `0`), `boot-capture.sh`'s `BOUND_AT` given the **same** bound so the two cannot fork |
| The plugin-once stamp survives a boot epoch that cannot be resolved | plugin updates skipped forever on such a host | unresolvable epoch falls back to per-start updates, logged. **And the gate's reaper does not touch those stamps** — they are written under `with_lock`, and an unlocked delete from every waiter every 2 s re-arms the amplifier PR A removed |
| The change has **no canary window** and is deployed as if it had one | `lib/start-bot.sh` is read per bring-up, so the pull is the rollout and the first keepalive bounce runs the new gate on a bot nobody chose | F17: PR B names the carrier, the pre-pull evidence and the rollback unconditionally; the temporary arming flag is the open half |

| The systemd leg is proven by test only | "divergence between the two supervisors is impossible" is not evidenced by a live boot on the supervisor that changes most | stated as a **bound, not an omission**, per the operator's deploy ruling; F11 removes the systemd-only change from this program's scope entirely |

Critical path: A's `BootPolicy` → A's `bot.conf` keys → A's gauntlet → A's deploy **(done)** → **B's Task 0 control reboot** → B's Task 1 (gate library) → B's Task 2 (marker + door tables + harness) → B's gauntlet → B's deploy → **the A+B reboot** → C.

The control reboot is on the critical path deliberately: it is the only measurement that can tell the gate's marginal value from PR A's, it costs one already-budgeted reboot, and either outcome changes what PR C is for.

## What NOT To Do

- Do not add a second bring-up mechanism, and do not leave the first one in place. F9 is the whole point: seven reworks of the same forty lines, none of which removed a predecessor.
- Do not add an operator knob. Every value ships in the package `system.yaml` `host.boot` block or is derived; the `lib/`-internal call conventions (`BOOT_ADMISSION_CALLER_CAP_S`, `BOOT_ADMISSION_POLL_S`, `BOOT_ADMISSION_CLAIM_GRACE_S`) are documented as **not** knobs, which is their right-moment surface.
- Do not invoke `systemctl` or `launchctl` outside `lib/supervisor.sh` in any file this work touches.
- Do not make the gate a hard requirement: every failure path proceeds and discloses. And do not let "proceeds" mean "proceeds all at once".
- Do not retire an old mitigation and first-exercise its replacement in the same deploy (F11), and do not deploy to the Pi.
- Do not widen the scope to the 80-odd grandfathered call sites; they shrink in follow-ups under the ratchet.
- Do not touch `library/`, fleet manifests, or any operator `.env`.
- Do not claim a criterion the instrument cannot discriminate. A proof that cannot fail for the right reason is not a proof, and this plan says so where that is true of it.
