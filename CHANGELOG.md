### Removed — F18 closure R1: the legacy writers, and the switch that gated the plane (#1467)

- **The plane is the only recorder, and it is always on.** Every legacy append is gone: `dispatch-task.sh` writes no `state/dispatch-log.jsonl` (the row is still composed, for the content key an id-less dispatch's `dispatch-log:sha:<key>` ref derives from — nothing writes it); `report-back.sh` writes no `report-back.jsonl` and greps no dispatch log (its join is the plane lookup alone); `emit_fleet_event` writes no `data/events/fleet-*.jsonl` / `state/events/` line — the system event is the record, waited on and bounded (`FLEET_EVENT_EMIT_TIMEOUT_S`, default 10), a failed or reaped emission DISCLOSED as not recorded; `keepalive.sh` writes no `keepalive-*.jsonl` (the file had no reader; the per-tick verdicts ride the heartbeat sample) and its BUSY/IDLE ticks emit nothing; `bot-vitals.sh` appends nothing and reaps nothing; `workstream-update.sh` is plane-only (below). With them go `plane_write_retired`, `plane_retirement_covers`, `plane_door_key`, `plane_fleet_tier_value`, `plane_emit_detached` and `rotate_jsonl_by_ts`, and the `PLANE_LEGACY_WRITE_*` flags mean nothing to a door any more (the composer still stamps them; R3 removes the flag surface).
- **`plane_armed` arms unless `PLANE_EMIT_DISABLED=1`** — `PLANE_EMIT_ENABLED` is no longer read by any door or hook (`plane-telegram-in/out`, `plane-session-start`, `plane-rc-relay-out` gate only on the exemption). Measured on the data flip: the pre-stop hook of every restarted bot ran with no flag in its environment and wrote its `handoff_skipped` into a legacy file the retirement had frozen — an env-gated arming loses records the day the file is gone, and a dispatch or report must land SOMEWHERE. An unrecorded dispatch or report is now said LOUDLY on stderr (`did NOT record … sending anyway; there is no other record`); a door with no fleet in its environment discloses and records nothing.
- **`workstream-update.sh` — the plane IS the registry.** Every verb materializes the registry from the plane (`plane-lookup.py --workstreams --or-empty`) INSIDE its lock, once per process; the verb's plane event is the write; no `workstreams.json`, no `workstreams-archive.jsonl` (the `archived` events are the archive; `prune` takes no `--archive`). A plane that cannot serve the registry refuses (rc 3), an unrecorded verb refuses (rc 4) with nothing changed, a silenced plane refuses (rc 3) — never a stale file. The R1 gauntlet found three defects in the A2 door that the file had hidden: the first open of a FRESH fleet could not happen (the plane holds no identity for a fleet before its first row; `--or-empty` starts from the empty registry, under any existing root), archived ids were invisible to the slug dedup (a re-opened title re-minted the archived id and ingest refused it — the writer's render now carries the archived ids), and the registry was materialized before the lock (two concurrent opens dedup'd against a stale snapshot). `with_lock`'s mkdir spinlock waits 30s (`WITH_LOCK_WAIT_S`), not 5: a critical section through the cold-CLI rung runs 1-2s, and a waiter that gives up runs UNLOCKED.
- **A door with no fleet anywhere anchors on the HOST, never silence.** Host jobs (disk-monitor, host-health-check, a sibling pull) carry no fleet, and the fleet-level `state/events/` file used to take their FLEET ALERT receipts; `emit_fleet_event` now lands them under the plane's host sentinel (fleet `_host`, subject_kind `host`, the hostname — the host probe's own convention; the legacy row renders with bot `host`). A bot-anchored call with no fleet in its environment reads the bot's own bot.conf (plane_peer_fleet's rule) — the pre-stop hook's exact shape. Found by the harness port: without this, host alerts were recorded nowhere.
- **fleet-pulse no longer gates its dispatch pre-sweep on the dispatch log existing** (`--all`, `--orphans`, `--unassigned` ran only `if [ -f "$dispatch_log" ]` — on a host whose files are gone the whole overdue/orphan/idle sweep silently switched OFF; found by the harness port). The fleet scripts (`fleet-pulse.sh`, `reload-fleet.sh`, `weekly-worker-restart.sh`) export `CLAUDLOBBY_FLEET` from their positional fleet, so a hand run anchors its events like the timer unit does.
- **The report door's resolver no longer gates on the retired file.** `report-back.sh` ran its `--open-task` resolver and its supplied-id check only `if [ -f "$_rb_dispatch" ]` — the dispatch log — so on a host whose files are gone a report without `--task` closed nothing (found by the R1 gauntlet through the real doors). The matcher answers from the plane under the flip; the retired paths only fill its positional slots until R2 removes them.
- Tests: the file-mode suites moved to a plane rig (`test_workstream_update.py`, `test_task_id_dispatch.py`, `test_dispatch_type.py`, `test_plane_door_e2e.py`); every "dormant without arming" pin became a positive pin of the always-on contract with a sibling pinning the exemption; the four-fact, dual-write and flag-carrier pins are gone with the machinery; `lib/validate-bot-change.sh` reads the plane.

### Fixed — the legacy importer fits an over-cap summary instead of refusing the report (#1467 chunk D)

- **The fleet's error breadcrumb never fired for a failure inside a shell function — the majority of the surface it exists to cover (#844).** A bash `ERR` trap is not inherited by shell functions unless `errtrace` is enabled, and `install_error_trap` set a bare `trap … ERR`: **47 `lib/` scripts call it, none enabled `errtrace`**, and `lib/` does nearly all its work in functions. Under the shipped `set -euo pipefail` shape a failure inside a function exits the script with **zero rows written** — verified against the real `install_error_trap`/`emit_script_error` with an isolated ledger: in-function failure 0 rows, the identical failure at top level 1 row, the function boundary being the whole difference.   Arming it fleet-wide was assumed to be high blast radius and measurement disproved that. **`errtrace` is control-flow neutral**: it changes only whether the trap runs, never whether a script continues or aborts, which narrows the risk from execution semantics to handler side effects and row volume. And **deliberate tolerance stays silent**: bash suppresses the `ERR` trap in the same contexts it suppresses `errexit` — `f || true`, `if f`, `f && g`, `! f`, `while f`, `( f )` — and that suppression is inherited by callees, transitively, so a failure three frames inside a function called under `|| true` emits nothing. That covers `lib/`'s **724** `||` sites, **691** `if`/`while` conditions and **172** `|| true` tails. Row volume is **one per failure** under `errexit`, which aborts before the status can propagate up the stack (without it, one row *per frame*); all 47 callers set it. `_lc_cleanup`, which runs on every script exit across all 47 and would have flooded the ledger fleet-wide, is `|| true`-guarded and emits nothing.

  **The static bound on false positives was measuring the wrong shape, and the full suite caught it.** `local v=$(fail)` fires and survives (the declaration's own status is 0) and `lib/` contains zero of those — true, re-derived against a positive control, and beside the point: the real class is any benignly-failing statement in a non-suppressed position inside a function, and `fleet-pulse.sh`'s `_readback_efiles` is one. It ends `done | sort -u` then `return 0`, so a bot with no ledger file for the span makes the last `[ -f ]` the pipeline's status under `pipefail`; the `return 0` masks that for `errexit` — that *is* the #610 fix — but the trap has already fired. A normal empty span logged a `script_error` every pulse, on the per-minute path. The codebase's own status-masking idiom was the false-positive generator. Fixed with `|| true` at the failing statement, which is what actually marks a non-zero as intended: `return 0` hides it from `errexit` while leaving the other reader — the trap — believing it saw a real fault. Caught by `test_fleet_pulse_no_events`, confirmed against a clean tree in both directions rather than filed as a known-flaky.

  A second cost is characterised rather than hidden: a **failing command substitution emits at both frames** — once at the true failure line inside the substitution's own subshell, once at the substitution's line in the parent, which `errexit` cannot abort on because the enclosing command's status is its own.   The hazard the issue did *not* name is latent: **under `errtrace` the trap fires inside the failing command substitution**, so any handler stdout is captured as the caller's value — `local v=$(fn)` silently becoming the handler's output, with no error and no row. `emit_script_error` is stdout-clean today, so this is one stray `echo` away rather than live; the handler's stdout is now discarded at the trap, and a test pins `emit_script_error`'s own stdout-cleanliness on the direct-call path (`notify-behind.sh` calls it outside any trap) so the guarantee belongs to the function rather than to one call site's redirect.

The ERR-records/EXIT-emits hybrid remains the right end state but needs `EXIT`-trap chaining with `_lc_cleanup` plus three caller traps, which is #523's territory; deliberately not folded in.

- **`overdue_dispatch` stops crying wolf over finished work (#835).** Four alerts fired within thirteen seconds, all four false — every bot had a live spinner and a fresh `.last-tool-call`, and three had already reported completed work. An id'd dispatch closes ONLY on a terminal report echoing the same `task_id`, and workers call `report-back.sh` without `--task`: **15 of the 20 terminal reports in the live ledger carried no id**, so every id'd dispatch stayed open until it aged out and the watchdog alarmed over work that was done. Two independent fixes. (1) When `--task` is omitted, `report-back.sh` now resolves the bot's **oldest** still-open dispatch and stamps that id into the report — the common path is correct by default instead of by discipline. This deliberately does **not** loosen the watchdog's join, which is strict on purpose (blanket-closing on any id-less report was the #447 bug class): the join is untouched, and only the id the report should have carried is supplied, resolved by `dispatch-overdue.py` so "which dispatch is open" has one definition rather than two that can drift. Oldest, not newest, and that distinction is the whole fix: multiple open dispatches are the normal case (measured live: **6 of 8** bots carry two or three), a worker is a serial session draining its queue in FIFO order, and the oldest row is the one actually past its deadline — the newest is usually still inside it. Resolving newest-first would close the quiet row and leave the loud one open, so the fix would not have reached the alarms it exists to stop; on the incident data it would not even have closed the author's own alarming row. FIFO also self-corrects: one report closes exactly one dispatch, so N reports for N queued tasks retire them in the order they were sent, and a worker that reports once still leaves the unreported rows open, which is the honest outcome. Resolution is gated to terminal statuses, since a `progress` report closes nothing. It is fail-open at every step — no `python3`, no ledger, or nothing open all leave the report exactly as it behaved before, because a report-back must never fail on an unavailable watchdog helper. (2) A past-deadline row whose worker **respawned** after the dispatch is split out of the overdue set: the session holding the id is gone, so the id can never be echoed and the row would alarm every cycle until `max_age`. The predicate is respawn, not session-absence — a restarted bot keeps its session *name*, so an existence check reads a fresh incarnation as the original one; `data/.spawn` (touched on every `start-bot.sh` run, the same marker `bridge_down_state` grades from) dates the current incarnation. Only id'd rows can orphan, since an id-less dispatch closes on any later terminal report and so survives a respawn intact. Orphans go inert for **alerting** exactly as an aged-out row does (#460), but are not simply swallowed: an aged-out row is an abandoned task, whereas an orphan is work the fleet lost to its own restart, which is actionable. `fleet-pulse` records each one **once** as a `dispatch_orphaned` event — latched on task-id set membership rather than a time window, because orphan-ness is monotonic, which needs none of `debounce_notify`'s machinery (itself reported broken in #831) and also survives the marker moving. They are listable via a new `--orphans` mode. This issue's own framing is that a tool going quiet defeats the operator just as a tool crying wolf does (#826/#831/#833), and trading one for the other would have been no fix at all. Net on cold start: start-bot's two sends drop from 2.1s to 1.0s. Empirically validated against a real Claude Code TUI, not a fixture: a command left unsubmitted at the prompt is missed by `tail -3` and caught by the new verify; a 1054-character payload collapses to `[Pasted text #2]` and is caught only by the placeholder branch; a 125-character payload wraps across the input box so that the full text matches no single rendered line and only the capped probe finds it; a clean submit leaves the box empty and fires no retry; a send queued against a busy pane leaves only the TUI's own hint text and fires no retry. `lib/validate-bot-change.sh` passes 95/0 with all three original call sites exercised live — and its two TUI fixtures, which had been drawing the prompt as the *last* line of the pane and so would have blessed the dead verify forever, now draw the footer below it (mutation-checked: widening the verify back to the whole pane turns that assertion red). - **Keepalive event retention now honors the fleet retention window.** `lib/keepalive.sh` reaped `keepalive-*.jsonl` on `KEEPALIVE_REAP_DAYS`, which is never composed into `bot.conf` and so always fell back to a hardcoded 7 days — diverging from `fleet-pulse.sh` and `bot-vitals.sh`, which reap `fleet-*.jsonl` on the composed `OBSERVABILITY_REAP_DAYS` (`observability.reap_days`). A fleet that set `reap_days: N` retained its pulse/vitals events for N days but its keepalive events for only 7. `KEEPALIVE_REAP_DAYS` now falls back to `OBSERVABILITY_REAP_DAYS` (then 7), so all three event writers reap on one window; an explicit `KEEPALIVE_REAP_DAYS` still overrides. Verified: with `OBSERVABILITY_REAP_DAYS=1`, a 3-day-old keepalive JSONL is reaped and the current day's is retained.
- **`claudlobby diff` vs. `claudlobby generate` fleet-timer divergence.** `diff_fleet_timers` built a 2-attribute shadow `Paths` object and handed it to `compose_fleet_timers`, instead of a real `Paths` instance; the moment the timer path read any other `Paths` attribute, `claudlobby diff` would raise `AttributeError` while `generate` kept working. Now passes a real `Paths` plus a temp output dir, with a regression test asserting the two commands exercise an identical `Paths` surface (#442).
- **Three runtime sweeps could resurrect departed bots' directories.** `git-pull-all.sh`, `reload-fleet.sh`, and `weekly-worker-restart.sh` acted on every directory under `runtime/bots/` without consulting `fleet.yaml`, so a cron/timer tick could re-create and poke orphaned directories for bots no longer declared in the fleet (surfacing as false "orphan" reports elsewhere in supervision). All three now consult the shared `bot_in_fleet` predicate before acting (#419, #448).
- **Dead code removed and Telegram-handle validation unified.** Dropped four unreferenced symbols (`McpEntry.is_multi`, `McpEntry.server_names`, `ValidationReport.merged_for_strict`, the legacy `loader.load_library_items`) and collapsed two divergent telegram-handle regexes into one `_TELEGRAM_HANDLE_RE` shared by `compose_bot_conf` and `compose_bot`, so a handle can no longer be accepted by one composition path and silently dropped by the other. Also fixes a latent `NameError` under `typing.get_type_hints` in `composer.py` (#430, #431).
- Fixed a `test_uptime` aggregate test that hardcoded a 2026-05-17 timestamp and had been silently failing (then deselected from CI) since the following day; it now stamps a relative timestamp so it stays in-window regardless of the calendar date, and CI re-enables the test (#444, #446).
- **MCP-trust allowlist no longer wiped by `generate`.** `settings.local.json` now emits a per-server `enabledMcpjsonServers` allowlist derived from the bot's composed MCP servers, re-derived on every `generate` instead of being lost, so a headless `claude --permission-mode auto` boot no longer stalls on an MCP-approval prompt after a daily `reload-fleet`. Fails closed: servers outside the fleet-configured set still prompt rather than being blanket-trusted (#453 Phase 4, #465).
- **Keepalive no longer misreads a busy bot as idle.** Liveness detection depended on a braille spinner plus a hardcoded verb list, which missed bots on newer TUI states (whimsical verbs, reduced-motion) and risked injecting reload keystrokes into a bot that was actually mid-task. Liveness now keys off the same `.last-tool-call` marker fleet-pulse already trusts, plus the "esc to interrupt" active-turn affordance, erring toward treating a bot as active (#472).
- **`overdue_dispatch` no longer re-fires forever for an abandoned dispatch.** A dispatch that never received a terminal report re-emitted an `overdue_dispatch` event on every fleet-pulse cycle indefinitely (one case produced 232 events from a single ~19-hour-old dispatch). The matcher now expires dispatches past a max age (default 24h, `DISPATCH_OVERDUE_MAX_AGE_S`, disable with `<=0`) (#460, #466).
- **`claudlobby generate` failing under systemd/launchd supervision.** `Paths.detect()` only walked up from the process's working directory, but the daily `reload-fleet` timer unit exports `CLAUDLOBBY_ROOT` while running from the supervisor's default cwd -- so `generate` died with `FileNotFoundError` before composing anything. `detect()` now resolves in explicit precedence order (hint > `CLAUDLOBBY_ROOT` env > cwd walk-up), and generated systemd/launchd timer units pin `WorkingDirectory=<root>` so no timer job depends on its spawn cwd (#479).

### Security

- Restrict .env file permissions to 0o600 (owner read/write only) in scaffold_env_files and env-migrate. Previously these files were created with default umask (typically 0o644), making fleet secrets world-readable on shared hosts.
