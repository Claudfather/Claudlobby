### Fixed

- **The documented regression diff could not detect a regression, and could invent one ([#1035](https://github.com/Claudfather/Claudlobby/issues/1035)).** `CLAUDE.md`'s `pytest -q --tb=no | grep ^FAILED | sort` → `comm -13` recipe — the instrument every contributor is told to use, and the *only* evidence available during the 2026-08-06 GitHub Actions outage — was wrong in **two independent directions**, and the fix needs two changes that are each the sole defense for one class. **Blind:** `addopts = "-rs"` (added for #1012) *replaces* pytest's default `fE` reportchars rather than adding to them, because `-r` is store-not-append — so no `FAILED` line is ever printed, both files come out empty, and `comm -13` reports zero introduced failures **unconditionally**. Three further modes produce the same empty diff for different reasons: a collection error prints `ERROR` not `FAILED` and aborts the whole suite (rc 2, count line reads `1 error`, so a count check misses it too); nothing collected (rc 5); and no `.venv`, e.g. run from the shared install rather than a checkout (rc 127, message on stderr, which the recipe also discarded). **Phantom:** the opposite failure — `ERROR: file or directory not found:` on a bad path or flag (rc 4) *matches* the pattern, so a typo in the *after* run fabricates a regression that does not exist; `log_cli` output and captured-log blocks do the same at rc 0 and rc 1. **Counts, because the baseline is not green:** the recipe now also diffs the `N failed, M passed` line, and on this suite that is the load-bearing signal rather than a hedge. `CLAUDE.md` records a baseline of **34 failed / 2125 passed**, so `rc = 1` is the *normal, expected* state of both the before run and the after run — which makes the exit-code gate structurally incapable of separating a healthy 34-failure baseline from a 38-failure baseline-plus-four-regressions. The gate can only ever discriminate *did not complete* (rc 2 / 5 / 127); counts are the only one of the three checks that answers **how many**, the one axis that actually moves on an already-red suite. Counts are also the last survivor when the names mechanism itself breaks — precisely what #1012 did here: measured, `1 failed, 20 passed` printed correctly while `grep "^FAILED"` returned zero lines and no summary banner was emitted at all, so names died, `rc` stayed 1, and the diff landed *inside* the evidence band reading clean. The three checks therefore cannot substitute for each other: **the exit-code gate** is the only thing that sees rc 2 / 5 / 127 (scoping is blind — those emit no summary block at all); **scoping to the `short test summary info` block** is the only thing that sees the rc 0 / rc 1 phantoms (the gate is blind — those exit *inside* the band it certifies); **the count line** is the only thing that sees either a magnitude change on a red baseline or the names mechanism failing (both others read `rc 1` and an empty name diff as clean). A count change with an empty name diff is evidence the names mechanism is broken, not a clean run; counts remain a cross-check rather than a substitute, since they miss rc 2, where the gate covers. Ravi validated counts-plus-names on ai-platform under this same bug, catching **four** real regressions the documented recipe called clean; clog established the baseline-is-red reasoning. Scoping also makes `--tb=no`, verbosity and `log_cli` irrelevant by construction, retiring an earlier and incorrect "keep `-q`, not `-v`" rule — verbosity was never the trigger. The recipe now redirects rather than pipes, which is load-bearing and not style: piping captures *grep's* status, which is only ever 0 or 1, laundering every broken mode into the evidence band so the gate passes silently — the `${PIPESTATUS[0]}` trap this file already documents for `gh api ... | head`, eating the very check built to escape it. All seven modes measured on pytest 9.0.3 (naive count → scoped count): `log_cli` passing rc 0 `1→0`; no `--tb=no` with one real failure rc 1 `2→1` (phantom killed, real one kept); normal failure rc 1 `1→1`; collection error rc 2 `1→1`; bad path rc 4 `1→0`; nothing collected rc 5 `0→0`; absent binary rc 127 `0→0`; `-q` and `-v` identical under scoping.

- **Two npx-cache probes that could not fail now can ([#851](https://github.com/Claudfather/Claudlobby/issues/851), [#852](https://github.com/Claudfather/Claudlobby/issues/852)).** Both keyed a verdict off an *absence* and attributed that absence to exactly one cause. **`claudlobby warm-cache`** ran `subprocess.run` without `check=True` and never read `.returncode`, so "no exception was raised" meant "the warm worked" — a child that simply exits non-zero never reached `failed`, fell through to `cache warm complete`, and returned 0, while `capture_output=True` discarded the diagnostic that would have explained it. It now classifies each package as cached, global, or missing, names global installs individually with the reason they will never appear in the cache, and fails only on genuine absence. The global root resolves lazily on the first cache miss (measured: **0** `npm` spawns when everything is cached — the normal `reconcile-fleet` path — and exactly **1**, not one per package, when the probe is needed). - **The fleet's error breadcrumb never fired for a failure inside a shell function — the majority of the surface it exists to cover (#844).** A bash `ERR` trap is not inherited by shell functions unless `errtrace` is enabled, and `install_error_trap` set a bare `trap … ERR`: **47 `lib/` scripts call it, none enabled `errtrace`**, and `lib/` does nearly all its work in functions. Under the shipped `set -euo pipefail` shape a failure inside a function exits the script with **zero rows written** — verified against the real `install_error_trap`/`emit_script_error` with an isolated ledger: in-function failure 0 rows, the identical failure at top level 1 row, the function boundary being the whole difference.   Arming it fleet-wide was assumed to be high blast radius and measurement disproved that. **`errtrace` is control-flow neutral**: it changes only whether the trap runs, never whether a script continues or aborts, which narrows the risk from execution semantics to handler side effects and row volume. And **deliberate tolerance stays silent**: bash suppresses the `ERR` trap in the same contexts it suppresses `errexit` — `f || true`, `if f`, `f && g`, `! f`, `while f`, `( f )` — and that suppression is inherited by callees, transitively, so a failure three frames inside a function called under `|| true` emits nothing. That covers `lib/`'s **724** `||` sites, **691** `if`/`while` conditions and **172** `|| true` tails. Row volume is **one per failure** under `errexit`, which aborts before the status can propagate up the stack (without it, one row *per frame*); all 47 callers set it. `_lc_cleanup`, which runs on every script exit across all 47 and would have flooded the ledger fleet-wide, is `|| true`-guarded and emits nothing.

  **The static bound on false positives was measuring the wrong shape, and the full suite caught it.** `local v=$(fail)` fires and survives (the declaration's own status is 0) and `lib/` contains zero of those — true, re-derived against a positive control, and beside the point: the real class is any benignly-failing statement in a non-suppressed position inside a function, and `fleet-pulse.sh`'s `_readback_efiles` is one. It ends `done | sort -u` then `return 0`, so a bot with no ledger file for the span makes the last `[ -f ]` the pipeline's status under `pipefail`; the `return 0` masks that for `errexit` — that *is* the #610 fix — but the trap has already fired. A normal empty span logged a `script_error` every pulse, on the per-minute path. The codebase's own status-masking idiom was the false-positive generator. Fixed with `|| true` at the failing statement, which is what actually marks a non-zero as intended: `return 0` hides it from `errexit` while leaving the other reader — the trap — believing it saw a real fault. Caught by `test_fleet_pulse_no_events`, confirmed against a clean tree in both directions rather than filed as a known-flaky.

  A second cost is characterised rather than hidden: a **failing command substitution emits at both frames** — once at the true failure line inside the substitution's own subshell, once at the substitution's line in the parent, which `errexit` cannot abort on because the enclosing command's status is its own. Both rows are true and carry different line numbers, so they are pinned by a test rather than deduped (dedup costs handler state and loses the more precise of the two). This is the change's other new-row source, since `echo "$(…)"` is a shape `lib/` contains ~64 of: silent today, two rows and a still-running script after. **Coverage bound:** static analysis cannot enumerate this class — it already missed one shape — so the 2,095-test suite and `validate-bot-change.sh` are the real instrument, and anything they do not exercise is canary territory.

  The hazard the issue did *not* name is latent: **under `errtrace` the trap fires inside the failing command substitution**, so any handler stdout is captured as the caller's value — `local v=$(fn)` silently becoming the handler's output, with no error and no row. `emit_script_error` is stdout-clean today, so this is one stray `echo` away rather than live; the handler's stdout is now discarded at the trap, and a test pins `emit_script_error`'s own stdout-cleanliness on the direct-call path (`notify-behind.sh` calls it outside any trap) so the guarantee belongs to the function rather than to one call site's redirect.

  Trapping `EXIT` instead was the stronger-looking alternative — it catches only the fatal case, emits exactly one row, and has no false-positive class at all, including the `fleet-pulse` one above — and **#523 disqualifies it**: `lib-common.sh` already installs `trap '_lc_cleanup' EXIT`, whose `|| true` tail makes macOS bash 3.2 report exit 0 for the whole script, so an `EXIT`-based emitter would read `$?` as 0 and emit nothing on exactly the platform that needs it, and #523 further records that rc-capture inside the trap cannot repair this. The ERR-records/EXIT-emits hybrid remains the right end state but needs `EXIT`-trap chaining with `_lc_cleanup` plus three caller traps, which is #523's territory; deliberately not folded in.

  Because the whole de-risking argument rests on suppression propagating into function bodies, and that was measured on bash 5.2 while `/bin/bash` on macOS is 3.2, the premise is **pinned by a test rather than carried as a dated assumption**: new `tests/test_errtrace_bash32.py` runs the suppression matrix in a real `bash:3.2` container and asserts the version too, so a moved tag cannot silently pin 5.x. Deliberately not opt-in gated, unlike `test_freshbox_boot_harness.py` — that harness needs credentials CI lacks, whereas this needs only docker, which CI has, so an env gate CI never sets would make the pin a test that never runs. - **`overdue_dispatch` stops crying wolf over finished work (#835).** Four alerts fired within thirteen seconds, all four false — every bot had a live spinner and a fresh `.last-tool-call`, and three had already reported completed work. An id'd dispatch closes ONLY on a terminal report echoing the same `task_id`, and workers call `report-back.sh` without `--task`: **15 of the 20 terminal reports in the live ledger carried no id**, so every id'd dispatch stayed open until it aged out and the watchdog alarmed over work that was done. Two independent fixes. (1) When `--task` is omitted, `report-back.sh` now resolves the bot's **oldest** still-open dispatch and stamps that id into the report — the common path is correct by default instead of by discipline. This deliberately does **not** loosen the watchdog's join, which is strict on purpose (blanket-closing on any id-less report was the #447 bug class): the join is untouched, and only the id the report should have carried is supplied, resolved by `dispatch-overdue.py` so "which dispatch is open" has one definition rather than two that can drift. Oldest, not newest, and that distinction is the whole fix: multiple open dispatches are the normal case (measured live: **6 of 8** bots carry two or three), a worker is a serial session draining its queue in FIFO order, and the oldest row is the one actually past its deadline — the newest is usually still inside it. Resolving newest-first would close the quiet row and leave the loud one open, so the fix would not have reached the alarms it exists to stop; on the incident data it would not even have closed the author's own alarming row. FIFO also self-corrects: one report closes exactly one dispatch, so N reports for N queued tasks retire them in the order they were sent, and a worker that reports once still leaves the unreported rows open, which is the honest outcome. Resolution is gated to terminal statuses, since a `progress` report closes nothing. It is fail-open at every step — no `python3`, no ledger, or nothing open all leave the report exactly as it behaved before, because a report-back must never fail on an unavailable watchdog helper. (2) A past-deadline row whose worker **respawned** after the dispatch is split out of the overdue set: the session holding the id is gone, so the id can never be echoed and the row would alarm every cycle until `max_age`. The predicate is respawn, not session-absence — a restarted bot keeps its session *name*, so an existence check reads a fresh incarnation as the original one; `data/.spawn` (touched on every `start-bot.sh` run, the same marker `bridge_down_state` grades from) dates the current incarnation. Only id'd rows can orphan, since an id-less dispatch closes on any later terminal report and so survives a respawn intact. Orphans go inert for **alerting** exactly as an aged-out row does (#460), but are not simply swallowed: an aged-out row is an abandoned task, whereas an orphan is work the fleet lost to its own restart, which is actionable. `fleet-pulse` records each one **once** as a `dispatch_orphaned` event — latched on task-id set membership rather than a time window, because orphan-ness is monotonic, which needs none of `debounce_notify`'s machinery (itself reported broken in #831) and also survives the marker moving. They are listable via a new `--orphans` mode. This issue's own framing is that a tool going quiet defeats the operator just as a tool crying wolf does (#826/#831/#833), and trading one for the other would have been no fix at all. Empirically validated by replaying **the live ledgers that produced the incident**: at the real alert epoch the pre-fix matcher reproduces all four alerts with their exact elapsed values (198s/195s/189s/185s); after the fix two move to the orphan set (astrid and mason, both restarted after dispatch — the issue reported only one) and the remaining two clear once their reports carry the resolved id, leaving zero overdue and the two orphans still listed. Verified: with `OBSERVABILITY_REAP_DAYS=1`, a 3-day-old keepalive JSONL is reaped and the current day's is retained.
- **`claudlobby diff` vs. `claudlobby generate` fleet-timer divergence.** `diff_fleet_timers` built a 2-attribute shadow `Paths` object and handed it to `compose_fleet_timers`, instead of a real `Paths` instance; the moment the timer path read any other `Paths` attribute, `claudlobby diff` would raise `AttributeError` while `generate` kept working. Now passes a real `Paths` plus a temp output dir, with a regression test asserting the two commands exercise an identical `Paths` surface (#442).
- **Three runtime sweeps could resurrect departed bots' directories.** `git-pull-all.sh`, `reload-fleet.sh`, and `weekly-worker-restart.sh` acted on every directory under `runtime/bots/` without consulting `fleet.yaml`, so a cron/timer tick could re-create and poke orphaned directories for bots no longer declared in the fleet (surfacing as false "orphan" reports elsewhere in supervision). All three now consult the shared `bot_in_fleet` predicate before acting (#419, #448).
- **Dead code removed and Telegram-handle validation unified.** Dropped four unreferenced symbols (`McpEntry.is_multi`, `McpEntry.server_names`, `ValidationReport.merged_for_strict`, the legacy `loader.load_library_items`) and collapsed two divergent telegram-handle regexes into one `_TELEGRAM_HANDLE_RE` shared by `compose_bot_conf` and `compose_bot`, so a handle can no longer be accepted by one composition path and silently dropped by the other. Also fixes a latent `NameError` under `typing.get_type_hints` in `composer.py` (#430, #431).
- Fixed a `test_uptime` aggregate test that hardcoded a 2026-05-17 timestamp and had been silently failing (then deselected from CI) since the following day; it now stamps a relative timestamp so it stays in-window regardless of the calendar date, and CI re-enables the test (#444, #446).
- **MCP-trust allowlist no longer wiped by `generate`.** `settings.local.json` now emits a per-server `enabledMcpjsonServers` allowlist derived from the bot's composed MCP servers, re-derived on every `generate` instead of being lost, so a headless `claude --permission-mode auto` boot no longer stalls on an MCP-approval prompt after a daily `reload-fleet`. Fails closed: servers outside the fleet-configured set still prompt rather than being blanket-trusted (#453 Phase 4, #465).
- **Keepalive no longer misreads a busy bot as idle.** Liveness detection depended on a braille spinner plus a hardcoded verb list, which missed bots on newer TUI states (whimsical verbs, reduced-motion) and risked injecting reload keystrokes into a bot that was actually mid-task. Liveness now keys off the same `.last-tool-call` marker fleet-pulse already trusts, plus the "esc to interrupt" active-turn affordance, erring toward treating a bot as active (#472).
- **`overdue_dispatch` no longer re-fires forever for an abandoned dispatch.** A dispatch that never received a terminal report re-emitted an `overdue_dispatch` event on every fleet-pulse cycle indefinitely (one case produced 232 events from a single ~19-hour-old dispatch). The matcher now expires dispatches past a max age (default 24h, `DISPATCH_OVERDUE_MAX_AGE_S`, disable with `<=0`) (#460, #466).
- **`claudlobby generate` failing under systemd/launchd supervision.** `Paths.detect()` only walked up from the process's working directory, but the daily `reload-fleet` timer unit exports `CLAUDLOBBY_ROOT` while running from the supervisor's default cwd -- so `generate` died with `FileNotFoundError` before composing anything. `detect()` now resolves in explicit precedence order (hint > `CLAUDLOBBY_ROOT` env > cwd walk-up), and generated systemd/launchd timer units pin `WorkingDirectory=<root>` so no timer job depends on its spawn cwd (#479).

### Security

- Restrict .env file permissions to 0o600 (owner read/write only) in scaffold_env_files and env-migrate. Previously these files were created with default umask (typically 0o644), making fleet secrets world-readable on shared hosts.
