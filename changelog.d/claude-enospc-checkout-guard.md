### Fixed — two harness instruments no longer remove the folder they were started in when the disk is full

On 2026-11-21 a test run lost its whole checkout. `harness/rehearse-held-push.sh` and `harness/rehearse-debounce-recipient.sh` made their throwaway root with `ROOT="$(mktemp -d)"` and then `ROOT="$(cd "$ROOT" && pwd -P)"`, under `set -uo pipefail` with no `-e`. With the disk full, `mktemp` failed and printed nothing; `cd ""` succeeds in bash without moving, so `ROOT` became the folder the script was started in, and the exit trap ran `rm -rf "$ROOT"`. pytest starts both instruments from the checkout (`tests/test_held_push_harness.py`, `tests/test_debounce_recipient_harness.py`), so the checkout was the folder removed. Started from a home folder, either script would have removed that. A private `TMPDIR` does not help on macOS, where a bare `mktemp -d` ignores it. Nothing in the wheel is affected: `harness/` is not packaged, and the runtime scripts and Python that remove folders already stop when their temporary folder cannot be made.

Both instruments now make their root through the new `harness/scratch-dir.sh`. `scratch_dir` stops the script with exit 3 and "Nothing was removed" unless `mktemp` really made a new directory. `scratch_remove` refuses a path that is empty, relative or the filesystem root, and a directory that is or holds the current directory, the directory the script was started in, or the home directory. The two test wrappers also start their instrument in a private directory, not the checkout.

`tests/test_harness_scratch_dir.py` runs both instruments with a `mktemp` that fails as a full disk makes it fail, from a throwaway folder, and fails on the old code because that folder is gone. Reproduced on a 600 MB disk image filled to the last block: before the fix the throwaway checkout on it was removed; after it, both scripts exit 3 and the checkout is intact.
