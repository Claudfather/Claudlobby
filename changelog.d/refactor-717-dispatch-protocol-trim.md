### Changed — the `dispatch` protocol keeps only what the fleet-ops guide does not already say (#717, #1674)

The `dispatch` protocol no longer repeats the fleet-ops guide that every bot composes. The admit, assign and deliver commands, the canonical IDs, request UUIDs, what to do after an uncertain outcome, the message door, the reads of current state, `task withdraw`, `reassign` and `escalate`, the result of `bot start` and `fleet reconcile` are now one pointer to the guide. What only the protocol said stays as it was: what the delivery file carries, admitting with the task's repo and project, the check-in assignment, zoned timestamps, the re-check and standing-goal rules, the worker preflight and its readiness gate, the shared-knowledge preflight and active-plan monitoring. A manager that composes the protocol carries 665 fewer tokens on every call (2,413 to 1,748, counted with Claude Code's own `/context`), from its first session after a host update. Whether managers dispatch as well, with these rules read once from the guide rather than twice, is not measured.
