### Added — run as root on Linux, the readiness probe reports the computer's accounts and setup's own records (#3144)

`host-readiness-v1` gains a last key, `logins`. It is null unless the probe runs as root (uid 0) on Linux. Then it is `{"team", "next_uid", "prepared"}`. `team` is `{"uid": N}` for the first `claudlobby` line in `/etc/passwd`, or null. `next_uid` is one past the highest uid or gid in 1000-59999 (passwd fields 3 and 4, group field 3, whatever the rest of the line holds), at least 1000, and null when that would pass 59999. The probe's header states this rule, and `tests/fixtures/next-uid-rule.json` pins it case by case, so the leaf can be tested against the same table. `prepared` lists at most two accounts, in receipt-name order, that have a completed System tools receipt in `/var/lib/claudlobby-browser-system/v1`, are still the first passwd line of that name with the receipt's uid, have a uid in 1000-59999, and are not `claudlobby`. No two entries share a name or a uid: two passwd names can share a uid, and the website refuses entries that do. Planned, unfinished and failed receipts, and ingress and index-refresh receipts, don't count. Only the receipt's top-level selection is read: the leaf writes sorted `ensure_ascii` JSON, so it is the last object in the file, and a test has the leaf write a receipt that the probe then reads.

`logins` is null when passwd or group is missing, is over 65,536 bytes or 512 lines, holds an all-digit id longer than 10 digits (refused before any numeric test), or has a `claudlobby` line without a numeric uid. `prepared` is null when the store or its parent is a symlink or not a directory, holds more than 128 `*.json` names, or a receipt read is over 98,304 bytes; symlinks and non-files in it are skipped, and scanning stops at the second account. The files are read with `dd` and matched with `case` patterns and field splitting; nothing read is executed, and the paths are fixed in the script. Output stays one line under 8 KiB (about 1.1 KB at most). The tests check every root answer against a copy of the website's rule for this key. Nothing a person sees changes until the website pins this probe, and the website must accept the new key first.

### Changed — the readiness probe runs its four tools by absolute path (#3144)

`uname`, `id`, `dd` and `tr` are now `/usr/bin/uname`, `/usr/bin/id`, `/bin/dd` and `/usr/bin/tr`, the same on macOS and Ubuntu, so `PATH` no longer chooses them. `command -v` still only looks up the prerequisite names.
