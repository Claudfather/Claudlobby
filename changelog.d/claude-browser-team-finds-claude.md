### Fixed — First team on a computer set up from the website: the bots find Claude and start

Nobody had launched a first team on a computer set up from the website yet; reading the code against a real one showed it would not start. Website setup installs one checked copy of Claude in the setup's own folder (`~/.local/share/claudlobby-browser/provider-bin/claude`) and puts no `claude` on that computer's path, but the bots still looked for `claude` on the path. Each bot would have stopped with "could not measure the configured Claude provider" before its window opened, and the launch would have waited out every bot and then refused to start the daily jobs. A computer set up this way now runs exactly that checked copy, for bots, version checks and scheduled jobs alike, and never another `claude` it might find on the path; if the checked copy is missing, the bot fails saying so. Computers set up from a terminal choose Claude exactly as before.

Two more stops were behind that one. Claude's first-run screens (a colour theme, then a notice) would have waited for a key in each bot's window, because the Claude profile kept for the bots had only ever been used to sign in. When a bot starts on a profile kept for the bots, its first-run onboarding is now marked done for the version that bot runs; everything else in the profile is left as it was, and the person's own `~/.claude` is not touched. Neither screen asks for consent. And the daily Claude update would have tried `npm install`, which that computer does not have and which could not update the checked copy anyway, then raised a failure alert every day. When the bots run the checked copy, the update job now writes one line in its log saying the setup owns that version and does nothing else.
