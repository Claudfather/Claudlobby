### Fixed — setup from the website on Ubuntu: a Python security update no longer stops setup for good

A computer prepared for setup from the website records the system Python that runs setup (its path and a SHA-256 of its bytes) in its preparation receipt, and the website keeps a hash of that record. Every later setup step and status read compared the file's bytes with the recorded hash. Ubuntu installs security updates by itself, and an update to Python replaces `/usr/bin/python3.12`, so from then on every setup step on that computer was refused (`installation_changed`, `identity_changed`), and the computer could not be prepared again because setup had already started.

On Linux, setup now checks what makes that file trustworthy and no longer compares its bytes: the receipt must still name the exact interpreter that is running, and that file must still be a regular executable in `/usr/bin`, owned by root and writable by nobody else, and `/usr/bin` itself must be a real folder (not a link) with the same owner and permissions. The setup step that reads the receipt gained the same ownership and place check. Anyone who can replace a root-owned file there already controls the computer, so the byte comparison added little and broke every computer on its first Python update. A preparation interrupted before an update also resumes after it.

What did not change: no receipt is rewritten. The recorded hash stays in the receipt and in the hash the website holds, so the website's record of each computer stays valid. A fresh preparation still records the hash. Claudlobby's own managed Python on a Mac is its own file and is still compared byte for byte. A different interpreter path, a file owned by someone other than root, or one others can write is still refused with the same names as before.
