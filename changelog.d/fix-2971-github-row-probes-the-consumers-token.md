### Fixed — the daily check's GitHub row probes the token the GitHub MCP server receives, and a declared GitHub App (#2971)

The daily credential check's `github_pat` row probed the first of `GITHUB_PERSONAL_ACCESS_TOKEN`, `GITHUB_TOKEN` and `GITHUB_PAT` that had a value, and reached the GitHub App only when none of them had one. The GitHub MCP server receives `GITHUB_PAT` alone: its fragment sets the server's `GITHUB_PERSONAL_ACCESS_TOKEN` from it. So with `GITHUB_PAT` empty and `GITHUB_TOKEN` set, the row probed `GITHUB_TOKEN` and could read `ok` while the server started with no token; and with the App's three variables complete beside a static token, the row probed the static token and never the App. On a tick the selected CLI starts, the row now probes what each surface that declares a GitHub credential hands its consumer: `GITHUB_PAT` for `mcp/github`, and the App for its three variables (the App's MCP fragment, or a bot routed through it with `github_app:`), even beside a static token. A declared `GITHUB_PAT` with no value is a `fail` naming the surfaces that declare it, and naming `GITHUB_PERSONAL_ACCESS_TOKEN` or `GITHUB_TOKEN` when one of them has a value. A fleet that declares both has both probed in the one row, which records the worse verdict and names each in its detail. A push token in `GITHUB_PAT` (`git_credentials`) is checked by that row alone, with or without a value. A direct run of `creds-check.sh`, which reads no declarations, probes as before.
