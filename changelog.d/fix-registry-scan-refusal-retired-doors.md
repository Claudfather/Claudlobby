### Fixed — first-fleet setup's registry-scan refusal names the command that resumes it (#2644)

When a fleet's `.env` tiers or the update command's environment set `PLANE_EMIT_ENABLED=0`, or the environment sets `PLANE_EMIT_DISABLED=1`, first-fleet setup refuses at its prepare stage, before it stops or starts anything. The refusal now names first-fleet setup and ends with `host update continue`, which resumes the retained update, instead of telling the operator to stage a new plan and activate it. The environment variable reference says the same. The getting-started guide's post-setup checks now name `fleet status`, which reports each bot's session and supervision, where they named `host status`, which reads only sealed-release records and reports a fresh setup as `unselected`.
