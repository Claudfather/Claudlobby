### Fixed — the credential check keeps a state file per fleet and checks only what the fleet declares (#1213)

Two defects stopped `creds-check.sh` from reporting a missing or dead credential. A direct run, one not started through `claudlobby host credentials check`, kept one state file for the whole host, `state/creds-check-state.json`, and fleets ticking minutes apart overwrote each other's verdict on the same keys: a run ended at every flip, so the skip escalation never reached day 3 and a dead token alerted as a fresh FAIL at age 0 each day instead of climbing its 1, 3, 7-day ladder. A direct run with a fleet now writes `state/creds-check-state.<fleet>.json`; root mode keeps its one file, and the old host file is left as it was. The selected CLI already passed each fleet `state/creds-check/<fleet>.json` (#1989), and its keys are unchanged, so a run there keeps its age across this update.

And every fleet's tick probed GitHub and both Railway tokens, whether or not the fleet used them, recording a token with no value as `skip`. A fleet whose bots declare the GitHub MCP and hold no token was never failed, though its MCP calls GitHub with no credential (public reads succeed, writes fail), and a fleet that never wanted Railway kept a lasting `skip` that from day 3 re-surfaced as "a permanent hole". The selected CLI now reads the credentials the activated roster declares, through the MCP fragments and integrations each bot is equipped with (`mcp_resolve.required_vars`, the walk the reconcile and doctor doors use), and passes them to the probe as `--declares VAR=SURFACE`. A bot whose git is routed through the GitHub App (`github_app:`) declares the App's three `GITHUB_APP_*` variables as well, under `mcp/github-app`, since the composer registers them for such a bot whether or not it is equipped with the App's MCP fragment. A declared credential with no value at the host, root or fleet tier is now a `fail` naming the surface that declares it; a credential no bot declares gets no probe, no row and no alert, and a row an earlier tick wrote for it is removed. A bot whose declarations cannot be read stops the check with an error, rather than reading as declaring nothing. The declarations are fixed before any `.env` tier is read, so a tier cannot declare or undeclare a credential: a tier line that tries stops the tick before any probe, with exit 2 and a line saying why, on bash 3.2 as on bash 5. A direct run has no declaration source, so it probes every provider and records a missing value as `skip`, as before.
