### Fixed — a usage refusal exits 2 when stderr cannot be written (#2935)

When stderr could not be written (a full device, a pipe whose reader had exited, fd 2 closed before Python started, or, under the installation launcher, a closed fd 2, in whose place the launcher hands the interpreter its runtime lock, open only for reading), a command line that the CLI's parser refused, such as an unknown command, exited 1 where a stderr on `/dev/null` gives 2: the parser's write of the usage and the error raised, and the command ended on that exception. The parser drops a write to stderr that fails now, so the refusal exits 2. With a working stderr it prints the same usage and error as before. A host update's arguments are read by the updater, which is not changed here, and a syntax refusal that a command answers with its own result (`invalid argument: command syntax`, printed on stderr without `--json`) still exits 1 on such a stderr.
