### Fixed — the Changelog fragment check judges a stacked PR by what its Files changed shows (#3024)

The check took a PR's base from the pull_request event, whose `base.sha` GitHub does not update when the base branch moves, so a PR stacked on a branch that had since merged the PR below it was charged with that PR's fragment (#3022). It now diffs from the live tip of the base branch, `origin/<base ref>`, and falls back to the event's sha only where the checkout has no such ref. An integration PR whose head collects reviewed sub-PRs with GitHub's merge commits (#2950) failed once per sub-PR, though each fragment was named after its own branch. It may now carry a fragment named after the head branch of a PR merged into it, when that PR's `Merge pull request #N from <owner>/<branch>` commit added it, and such a fragment must still be in the format. Any other misnamed fragment is still refused, including one a squash-merged sub-PR brought: a squash leaves no merge commit naming the branch.
