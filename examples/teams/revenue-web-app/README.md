# Revenue web-app team candidate

This single-file candidate composes a lead, a web-app engineer and an independent reviewer from shipped roles. It is intended for a bounded improvement to an existing approved GitHub repository, with tested task-branch PRs and a human deciding whether to merge and deploy. It has not demonstrated a business outcome, a selected reference deployment or a cold-host launch.

The lead uses `orchestration`, the engineer uses `software-engineering`, and the reviewer uses `code-review`. Existing clauDNA workflow plugins remain the package defaults; this example adds no plugin or role. The reviewer retains the shipped role's ability to write review scratch and memory rather than applying a misleading blanket Write/Edit deny.

Before using the candidate, customize its fleet name, unique service prefix, repository scope and approved goal. The example contains no credentials. Its account points to native Claude configuration; the operator must establish native authentication separately. GitHub MCP uses the shipped `github` fragment and its credential contract. Git/CLI access is a separate requirement: a GitHub browser login or a configured repository name is not verified host access. No Telegram channel, native remote-control connection, Vercel/Neon connection or private integration is selected.

The selected human path is core Plane/direct-owner access for input and visibility, after the operator independently establishes access and the relevant explicit action grants. The candidate does not initialize that authority or establish browser/ingress readiness. Bots coordinate through canonical task, assignment/report and message operations. Shipped orchestration and worker-lifecycle text still contains Telegram-specific instructions: composition omits channel flags, Telegram plugin selection and channel-derived tool grants, but does not rewrite that text. The lead's inherited `status`/`checkin` skills still contribute a Telegram reply allowance; this does not load the disabled plugin. The common mission explicitly skips Telegram posts/tools when no channel is enabled while retaining canonical reports. This does not supply unattended human alerts.

The existing sealed `fleet setup` command consumes this authored manifest through `--config`, with an explicit root, fleet and install directory. It activates the fleet and can start supervised processes; it is an operator action, not template validation. Follow the maintained [getting-started instructions](../../../documentation/getting-started.md) for release/prerequisite setup and the [fleet schema](../../../documentation/fleet-yaml-schema.md) for configuration. Existing declarations require explicit replacement; this example does not authorize overwriting another team.

The common mission requires human permission for merges, deployment, new spending beyond agreed provider usage and destructive data changes. Shipped `merge-policy-human`, `no-push-main`, `no-merge-own-pr`, `no-merge-admin` and `no-destructive-git` policies reinforce the Git boundary, and native permission bypass is disabled. The orchestration role still contains auto-merge/re-merge guidance; the lead's mission explicitly gives the human-merge guardrail precedence, states that reviewer approval alone is insufficient and leaves the merge itself to the human. This resolves instruction priority for the candidate, not through text removal or a technical approval gate for arbitrary shell commands, cloud deployment or data mutation. The candidate creates no standing external grant and does not claim that such effects are mechanically prevented.

Without an adjacent `projects.yaml`, the existing project owner derives review-tier projects from repository scope. `fleet setup` copies only `fleet.yaml`; it does not install adjacent project or mission files. Revenue-facing preview/acknowledgment policy requires a separately authored [project declaration](../../../projects.yaml.example) placed through the existing project/configuration owner before activation. This candidate uses an inline fleet mission and does not pretend to include that richer bundle. Revenue metrics are not supplied.

Static configuration/composition proof does not establish runtime behavior, provider readiness or useful work. Independent canary validation and the later cold-host/business trial remain required before those claims. Browser-guided team creation, repository preparation, credential delivery and launch authorization remain separate setup capabilities; this recipe does not complete that journey.
